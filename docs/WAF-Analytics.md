# Azure デプロイ アセスメント（Well-Architected Framework 突合）

対象：Campaign Flow（広告作品ライフサイクル管理デモ）
作成日：2026-10-30
基準：Azure Well-Architected Framework の 5 つの柱（信頼性・セキュリティ・コスト最適化・オペレーショナル エクセレンス・パフォーマンス効率）と、[Azure Container Apps のアーキテクチャのベスト プラクティス](https://learn.microsoft.com/azure/well-architected/service-guides/azure-container-apps)

> 判定の凡例：✅ 対応済み ／ ⚠ 一部対応・条件付き ／ ❌ 未対応 ／ ➖ 対象外。優先度：**P0**＝本番利用の前に必須、**P1**＝強く推奨、**P2**＝改善。

---

## 1. 結論

| 用途 | 判定 | 条件 |
|---|---|---|
| **デモ公開（社内テナント内・架空データのみ）** | **条件付きで可** | Entra ID の組み込み認証を必須にした状態で公開する（準備済み）。レプリカは 1 つ、データは再起動で初期化されることを許容する。 |
| **本番利用（実データ・複数利用者）** | **不可** | 第 5 節の P0（認証と権限の統合、永続データ、バックアップ、ネットワーク分離ほか）を解消するまで不可。 |

最大の論点は 2 つです。

1. **利用者の特定が認証ではない。** 画面右上の「視点」切替は `X-User` ヘッダーでユーザーを選ぶだけで、サーバーは信頼して受け入れます。ローカル専用なら問題になりませんが、クラウド公開では、サインインできる誰もが業務責任者などのペルソナを選べます。デモ用途の暫定策として入口で Entra ID 認証を必須にしました。本番では、検証済みの Entra ID の身元とアプリ ロールから権限を決めるよう作り替える必要があります。
2. **状態を持つ単一インスタンス設計。** データは SQLite（コンテナ内 `/tmp`）で、プロセス内ロックで排他しています。水平スケール・ゾーン冗長・バックアップは成立しません。デモでは「起動のたびに決定的な架空データを再投入」という性質を活かして許容し、本番では Azure SQL Database などのマネージド DB への移行が前提です。

## 2. 対象ワークロードの特性

| 項目 | 現状（根拠） |
|---|---|
| 構成 | Python 標準ライブラリのみの HTTP サーバー（[server.py](../app/server.py)）＋静的 UI（[static/](../app/static)）。外部サービス・外部 API・CDN への通信なし |
| データ | SQLite 1 ファイル（[db.py](../app/db.py)）。架空データを決定的に投入（[seed.py](../app/seed.py)、`SEED_VERSION`） |
| 状態 | サーバー内に全状態。`threading.RLock` の単一ロックで全 API を直列化 |
| 認証・認可 | `X-User` ヘッダーによるペルソナ切替と、役割・顧客単位の閲覧制御（[server.py](../app/server.py) `PERMS`）。**認証は無い** |
| 生成 AI | 使用していない。「AI Agent による最適化」は決定的なシミュレータと探索（[ops.py](../app/ops.py)）。 |
| 想定規模 | 少人数のデモ。要求定義書の性能目標（案件ビュー 3 秒以内など）は未検証 |
| 既定動作 | ループバックのみ。ホスト型は `APP_REMOTE_HOSTS` を明示した場合のオプトイン |

## 3. ホスティング先の選定

| 候補 | 評価 | 採否 |
|---|---|---|
| **Azure Container Apps（Consumption）** | コンテナーをそのまま実行でき、組み込み認証・マネージド ID・ログ連携・HTTPS 終端が標準。1 レプリカ固定、ゼロ スケールも選べ、デモのコストを抑えやすい。 | **採用** |
| App Service（コード デプロイ） | 同様に認証・ログ連携あり。Python 標準ライブラリのみで起動できる。ただしコンテナー前提の ACR・azd のフローから外れる。 | 次点 |
| AKS | 本件の規模に対して運用負荷が過大。 | 不採用 |
| Static Web Apps + Functions | API が単一プロセスの状態（SQLite・ロック）に依存するため大幅な作り替えが必要。 | 不採用 |

WAF のサービス ガイドは、新規のプラットフォームでは Container Apps の express も検討対象としています。本件はカスタム イメージ・認証設定・プローブを明示したいため、標準の Container Apps（ワークロード プロファイル環境）を選び、express は将来の簡素化の選択肢としました（機能が要件を満たすかは未確認）。

## 4. 5 つの柱ごとの突合

### 4.1 信頼性

| WAF の推奨 | 現状 | 判定 | 対応 |
|---|---|---|---|
| 正常性プローブ（startup / liveness / readiness） | `/healthz` を実装し、3 種のプローブを設定（[app.bicep](../infra/app.bicep)）。`/healthz` は Host 検査対象外で、情報を返さない | ✅ | — |
| 冗長性（HTTP アプリは 3 レプリカ以上） | **1 レプリカ固定**。SQLite を各インスタンスが持つため、複数にすると状態が分裂する | ❌ | デモは許容。本番は **P0**：外部 DB 化したうえで 3 レプリカ以上 |
| 可用性ゾーン | 環境は `zoneRedundant: false`（ゾーン冗長にはカスタム VNet が必要） | ❌ | 本番は P0：VNet 統合＋ゾーン冗長 |
| 状態の外部化・バックアップ | データは `/tmp`（再起動で消える）。復元できるのは「架空データの再投入」のみ | ❌ | デモは許容。本番は **P0**：Azure SQL Database（ゾーン冗長・PITR）等、RPO/RTO を定義 |
| 自動スケール | 不可（`maxReplicas: 1`）。単一ロックで直列処理 | ❌ | P1：DB 移行後に HTTP 同時実行ルールで水平スケール |
| 自己修復 | liveness 失敗で再起動。ただし再起動で状態は初期化される | ⚠ | 状態の外部化後に有効 |
| リージョン障害対策 | 単一リージョン | ❌ | 本番は P2：要求する可用性に応じて Front Door＋複数リージョン |
| 信頼性目標（SLO）・正常性モデル | 未定義。要求定義書の NFR-OPS-01（99.5%）は単一レプリカでは根拠が弱い | ⚠ | P1：SLO を決めて指標とアラートに落とす |
| 障害テスト | なし | ❌ | P2：再起動・DB 障害の演習 |

### 4.2 セキュリティ

| WAF の推奨 | 現状 | 判定 | 対応 |
|---|---|---|---|
| Microsoft Entra ID による認証 | Container Apps の**組み込み認証**で未認証を拒否（単一テナント、`authClientId` 必須）。`/healthz` のみ除外 | ✅（入口） | — |
| **身元に基づく認可（最小権限）** | **未対応**。アプリは `X-User` を信頼する。サインインした利用者なら誰でも全ペルソナ（業務責任者・監査を含む）を選べる。組み込み認証が付与する検証済みの身元ヘッダーは使っていない | ❌ | **P0**：検証済みの身元（`X-MS-CLIENT-PRINCIPAL`）または Entra のアプリ ロール／グループから役割・顧客スコープを決定し、`X-User` を廃止（またはローカル専用に限定） |
| マネージド ID・資格情報レスの接続 | ACR からの pull はユーザー割り当てマネージド ID（`AcrPull`）、ACR の管理者ユーザーは無効 | ✅ | — |
| シークレット管理（Key Vault） | 認証用のクライアント シークレットを Container Apps のシークレットとして保持（Bicep のセキュア パラメーター経由） | ⚠ | P1：Key Vault 参照、または**フェデレーション資格情報**でシークレット自体を廃止。ローテーション手順を定義 |
| 通信の暗号化（HTTPS 強制） | `allowInsecure: false`、HSTS 付与（ホスト型のみ）、Origin は https のみ許可 | ✅ | — |
| ネットワーク分離・プライベート エンドポイント | 外部イングレス（パブリック）。VNet なし | ❌ | デモは許容（認証で保護）。本番は **P0**：内部イングレス＋Application Gateway/Front Door（WAF）、プライベート エンドポイント |
| アウトバウンド制御 | アプリは外向き通信を行わない設計。ただしネットワーク レベルの制限は未設定 | ⚠ | P1：VNet 統合時に UDR・NSG で外向きを遮断 |
| Web 攻撃対策（WAF）・レート制限 | なし（アプリ層は CSP、Host/Origin 検査、POST は JSON のみ、入力検証） | ❌ | 本番は P0：WAF ポリシー（OWASP）とレート制限 |
| コンテナーのサプライ チェーン | 最小ベース（`python:3.12-slim`）、非 root（UID 10001）、依存パッケージなし。**ベース イメージの固定（ダイジェスト）・脆弱性スキャン・SBOM は未実施** | ⚠ | P1：ダイジェスト固定、Defender for Containers、CI でのスキャン |
| 保存データの暗号化・分類 | 架空データのみ（分類：公開可）。実データの場合、顧客の財務・与信・担当者情報を扱うため分類・暗号化・保持期間の定義が必要 | ⚠ | 本番は P0：データ分類、保存時暗号化（マネージド DB の既定）、保持・削除ポリシー |
| 監査ログ | アプリの監査ログは SQLite 内（再起動で消える）。要求（NFR-SEC・FR-OPS-04）の改ざん耐性を満たさない | ❌ | 本番は **P0**：Log Analytics／不変ストレージへ出力、保持期間 |
| ログの機微情報 | リクエスト ログはメソッド・パス・状態のみ（クエリ文字列・本文なし）。ただし URL パスに ID が入る | ✅ | — |
| 応答ヘッダー | CSP・`X-Content-Type-Options`・`X-Frame-Options`・`Referrer-Policy`、作品ページは別 CSP とサンドボックス | ✅ | `Server` ヘッダーのバージョン表示は軽微な情報露出（P2） |

### 4.3 コスト最適化

| WAF の推奨 | 現状 | 判定 | 対応 |
|---|---|---|---|
| 適正サイズ | 0.5 vCPU／1 GiB の 1 レプリカ。計算量は小さい（API は主にミリ秒オーダー。ただしネットワークを含む実測は未実施） | ✅ | 実測後に見直し |
| 従量課金の活用 | Consumption プロファイル。常時 1 レプリカ（状態保持のため）。**ゼロ スケールは可能だが、起動のたびに状態が初期化される** | ⚠ | 常時デモをしない期間は最小レプリカ 0 でコスト削減（許容できる場合） |
| SKU の妥当性 | ACR は Basic（デモで十分）。ゾーン冗長・プライベート リンク・ジオ レプリケーションが必要な本番は Premium | ✅ | — |
| ログのコスト管理 | Log Analytics の保持 30 日。取り込みはリクエスト ログとプラットフォーム ログ | ⚠ | P2：取り込み上限（日次キャップ）とアラート |
| コスト把握 | タグ付け（`azd-env-name`・`workload`・`dataClass`）済み。**月額予算（既定 100,000・請求通貨）を Bicep で作成し、実績 50/80/100%・予測 100% でメール通知**。実コストの見積りは未実施 | ✅ | Azure Pricing Calculator での見積り（P1） |
| 本番化時の追加コスト | 外部 DB、WAF（Application Gateway/Front Door）、VNet、Key Vault、複数レプリカが加わる | ➖ | 本番化の判断時に見積り（本書では金額を算出していない） |

### 4.4 オペレーショナル エクセレンス

| WAF の推奨 | 現状 | 判定 | 対応 |
|---|---|---|---|
| IaC・再現可能な展開 | Bicep（[main.bicep](../infra/main.bicep)・[app.bicep](../infra/app.bicep)）と azd（[azure.yaml](../azure.yaml)）。`az bicep build` で警告なしにコンパイル確認済み | ✅ | what-if の実行（P1） |
| CI/CD | なし | ❌ | P1：GitHub Actions（`azd pipeline config`）でテスト→ビルド→デプロイ。フェデレーション認証 |
| 監視・アラート | コンソール ログ（JSON 1 行/リクエスト）を Log Analytics へ。メトリックの閾値アラート・ダッシュボードは未設定 | ⚠ | P1：5xx 率・再起動回数・レイテンシのアラート、Workbook |
| 正常性とログの標準化 | `/healthz`、構造化ログ。トレース（OpenTelemetry）は無し | ⚠ | P2：Application Insights / OpenTelemetry |
| 自動テスト | 32 件（API・権限・翻訳・ホスト型モード）。コンテナー実行・負荷・UI の E2E は無し | ⚠ | P1：コンテナー起動のスモーク テスト、E2E |
| 安全な展開 | 単一リビジョン モード、ステージング環境なし | ⚠ | P2：複数リビジョンでのカナリア／ブルーグリーン |
| スキーマ変更 | 起動時の軽量マイグレーション（`_migrate`）と、デモデータの版管理（版が変わると**旧データを削除して再投入**） | ⚠ | 本番は P0：正式なマイグレーション ツールと、データ削除を伴わない更新 |
| ガバナンス | リソース グループ単位のタグ。Azure Policy は未適用 | ⚠ | P2：Container Apps 向けの Azure Policy（HTTPS 強制・パブリック アクセス制限など） |
| 運用手順書 | 本書と README の手順のみ | ⚠ | P1：障害対応・シークレット更新・復旧の手順 |

### 4.5 パフォーマンス効率

| WAF の推奨 | 現状 | 判定 | 対応 |
|---|---|---|---|
| 負荷に応じたスケール | 不可（1 レプリカ、全 API を 1 つのロックで直列化） | ❌ | 外部 DB 化とロック撤廃後に水平スケール（P1） |
| 性能目標の検証（NFR-OPS-02：3 秒以内） | 未検証。サーバー内の処理は軽いが、`ThreadingHTTPServer` ＋単一ロックのため同時利用で待ちが生じる | ❌ | **P1**：Azure Load Testing で実測（代表シナリオ） |
| 静的コンテンツの配信 | 全応答に `Cache-Control: no-store`。圧縮なし。d3 など数百 KB の資産を毎回転送 | ⚠ | P1：静的資産は長期キャッシュ＋ハッシュ付きファイル名、gzip/brotli（または CDN） |
| クライアント側の負荷 | 一覧画面で広告作品を iframe で複数表示（サムネイルは 2.2 秒で静止）。装飾 Canvas とグラフのアニメーション | ⚠ | 低スペック端末での確認（P2）。`prefers-reduced-motion` には対応済み |
| データ アクセス | SQLite のローカル I/O。外部 DB 化で遅延が増える | ➖ | 移行時に N+1・インデックスを確認 |
| リージョン配置 | 未決定 | ⚠ | 利用者に近いリージョン（例：Japan East。提供状況は要確認）を選ぶ |

## 5. ブロッカーと改善計画

### P0：本番利用の前に必須

| # | 項目 | 理由 | 方向性 |
|---|---|---|---|
| 1 | 認証と認可の統合 | `X-User` を信頼する設計では、サインインした誰でも全権限を取得できる | 検証済みの身元・Entra アプリ ロールから役割と顧客スコープを決定 |
| 2 | 永続データとバックアップ | 再起動で全データが初期化される | Azure SQL Database 等へ移行。RPO/RTO を定義し、復元を演習 |
| 3 | 冗長化 | 単一レプリカ・単一ゾーン | 外部 DB 化後に 3 レプリカ以上、ゾーン冗長（VNet 統合） |
| 4 | ネットワーク保護 | パブリック イングレス・WAF なし | 内部イングレス＋WAF、プライベート エンドポイント、アウトバウンド制御 |
| 5 | 監査ログの耐久化 | アプリ内ログは消える。統制要件を満たさない | Log Analytics／不変ストレージへ出力 |
| 6 | データ分類と保持 | 実データは財務・与信・担当者情報を含む | 分類、暗号化、保持・削除、取引先データの閲覧範囲の再確認 |
| 7 | 正式なマイグレーション | 版が変わると旧データを削除して再投入する | スキーマ移行ツールへ。データ削除を伴う動作を撤廃 |

### P1：強く推奨

シークレットの廃止または Key Vault 化／CI/CD／アラートとダッシュボード／コンテナーのスキャンとダイジェスト固定／負荷テスト／静的資産のキャッシュと圧縮／SLO 定義／予算アラート／運用手順書。

### P2：改善

OpenTelemetry／カナリア展開／Azure Policy／`Server` ヘッダーの非表示／ログ取り込み上限／障害注入テスト／マルチリージョン。

## 6. このリポジトリで実施したデプロイ準備

| 変更 | 内容 |
|---|---|
| ホスト型モード（オプトイン） | `APP_REMOTE_HOSTS`（許可ホスト名）を指定した場合のみ `0.0.0.0` にバインド可。未指定は従来どおりループバック以外を拒否。Host は許可リストで検査、Origin は https のみ許可、HSTS を付与、リクエストごとの JSON ログを標準出力へ |
| `/healthz` | プローブ用。Host 検査の前に応答し、情報を返さない |
| [Dockerfile](../Dockerfile) | `python:3.12-slim`、非 root、アプリのコードのみコピー。DB は `/tmp` |
| [infra/](../infra) | Container Apps 環境（Consumption）、アプリ（1 レプリカ・プローブ・https のみ）、組み込み認証（Entra・単一テナント、未認証はサインインへリダイレクト）、ACR（Basic・管理者無効）、ユーザー割り当てマネージド ID（`AcrPull`）、Log Analytics |
| [azure.yaml](../azure.yaml) | azd のサービス定義（ACR でリモートビルド。Docker 不要） |
| テスト | ホスト型モードの許可・拒否、`/healthz`、HSTS を単体テストで確認（全 32 件 OK） |

## 7. デプロイ手順

手順は [README の「Azure へのデプロイ」](../README.md#azure-へのデプロイ) に記載しています（Entra アプリ登録 → `azd up` → リダイレクト URI の登録）。

### デプロイ前チェックリスト

- [ ] 公開範囲が社内テナントのデモで、データがすべて架空であることを関係者が了承している
- [ ] Entra アプリ登録（単一テナント）を作成し、リダイレクト URI を登録した
- [ ] 利用するリージョンで Container Apps と ACR が利用可能で、クォータがある
- [ ] `azd provision --preview`（what-if）で変更内容を確認した
- [ ] 認証なしでアクセスできないこと、`/healthz` 以外がサインインを要求することを確認した
- [ ] 想定利用者に「視点切替は認証ではない」ことを周知した
- [ ] 予算アラートを設定した

| 料金 | 見積り未実施。月額予算 100,000 のアラートを作成済み（Pricing Calculator で確認すること） |

実施時の留意点：対象テナントのポリシーでアプリ登録のクライアント シークレットの有効期間は **30 日以内**（90 日は拒否）でした。期限が切れるとサインインできなくなるため、`infra/deploy.ps1` の再実行（シークレットの再発行と再デプロイ）か、フェデレーション資格情報への移行（P1）が必要です。

前提：初回の `azd provision` ではプレースホルダのイメージが使われ、`azd deploy` が完了するまでリビジョンは正常になりません。アプリ ロールやグループによる権限、Key Vault、VNet、WAF、外部 DB は本書の対象外（P0/P1 として計画）です。
